# LeakBase

국내 개인정보 유출 사고 아카이브 프로토타입. 사용자가 내가 쓰는 서비스를 등록하면 관련 유출 사고와 확인할 조치를 한곳에서 보여 준다.

| 항목 | 내용 |
| --- | --- |
| 현재 PRD 버전 | **0.5** (2026-11-16 ~ 11-17) |
| 기준 사이트 버전 | **v14** (zip·캐시 번호 `?v=14`) |
| 방식 | 순수 HTML·CSS·JavaScript, 저장된 JSON 사용(**API 미연동**), GitHub Pages 배포 |
| 팀 | 김태린, 윤수영 |

> 버전 번호는 두 가지다. **PRD 버전**(0.4, 0.5 …)은 이 문서의 기획·요구사항 버전이고, **사이트 버전**(v12 …)은 코드 zip과 캐시 번호다. 둘의 대응은 아래 [변경 이력](#1-변경-이력)에 기록한다.

## 1. 변경 이력

> 0.1~0.3은 2026-11-16에 교수님 요청에 따라 작업 기록(노션 주차별 문서)을 기준으로 사후 정리한 버전이다. 0.5부터 작업과 함께 기록한다.

### 1.1 버전 요약

최신 버전이 위로 오게 쌓는다.

| PRD 버전 | 사이트 버전 | 기간 | 요약 |
| --- | --- | --- | --- |

### 1.2 버전 관리 규칙

- PRD 버전은 변경이 있을 때마다 올린다(0.4 → 0.5 → …). 같은 PRD 버전 안에서 사이트 버전이 여러 번 바뀔 수 있다(0.5 = v13~v14). 사이트 버전(v12 …)과의 대응을 위 표에 함께 적는다.
- 새 버전을 낼 때 **이전 버전과 달라진 점**을 항목별로 기록한다: 기능, 폴더·파일 구조, 데이터 구조(필드·건수·허용값), 그 외, 변경 이유.
- 폴더 구조나 데이터 구조가 바뀌면 [1.4](#14-구조-스냅샷-prd-05--v14)의 **구조 스냅샷**도 새 버전 기준으로 갱신한다.
- 변경 이력은 최신 버전이 위로 오게 쌓는다. 한 번 적은 이력은 고치지 않고, 잘못된 것은 다음 버전에서 정정한다고 적는다.
- **새 버전(예: 0.6)을 낼 때 할 일**: ① 1.1 버전 요약 표에 한 줄 추가 ② 1.3에 새 버전 이력 추가 ③ 1.4 구조 스냅샷 갱신 ④ 맨 위 "현재 PRD 버전·기준 사이트 버전" 표 갱신 ⑤ PRD 본문(2.x) 수정

#### PRD 0.1 — 최초 정리 (3~5주차, 2026-09-21 ~ 10-12) *(사후 정리)*

이 버전은 비교 대상이 없는 **최초 정리**다. 사이트 코드는 없고 와이어프레임 HTML(`4주차_wireframe_LeakBase.html`)만 있었다. 근거는 노션 3·4·5주차 문서다.

##### 목적

- 주제: **개인정보·보안 유출 사고 아카이브**. 3주차에 팀원별 아이디어 6개를 비교해 최종 후보 2개로 좁힌 뒤 선정했다.
- 가치 제안: 유출 사고 뉴스에 불안한 이용자에게, 내가 쓰는 서비스를 기준으로 사고 이력과 권장 조치를 개인정보 입력 없이 한곳에서 보여 줘 무엇을 해야 하는지 바로 알 수 있게 돕는다. (불안 → 확인 → 행동)
- 트랙: 심화 트랙(최신 외부 API 반영). 필수 기능을 먼저 완성하고, 심화가 실패해도 직접 구성한 30건 이상의 JSON으로 핵심 흐름을 유지한다. API 종류와 호출 한도는 공식 문서 확인 후 확정(4주차 기준 11~12주차 판단).
- 초기안과 변경: 3주차 초안은 사고 사례를 조사·비교하는 학습 서비스(메인 타겟: 정보보안 전공 대학생)였다. 교수님 피드백(주제와 핵심 사용자의 일치)으로 불안한 일반 이용자를 메인 타겟으로 바꿨다.

##### 사용자

| 구분 | 내용 |
| --- | --- |
| 핵심 사용자 | 유출 뉴스에 불안한 일반 이용자(대학생 포함). 뉴스·사업자 통지를 접한 직후 내가 쓰는 서비스가 해당되는지, 무엇이 유출됐는지, 무엇을 해야 하는지 확인하려는 사람 |
| 보조 사용자 | 정보보안 전공 대학생. 별도 서비스 없이 같은 사고 데이터와 필터로 수용 |
| 통합 | 유출 통지를 받은 이용자는 핵심 사용자의 사용 상황 중 하나로 보고 상세의 권장 조치로 수용 |
| 제외 | 정보보안 분야 취업 준비생 |
| 페르소나 | 쇼핑·배달·통신·게임 등 여러 서비스를 쓰고, 유출 뉴스를 볼 때마다 내 계정도 해당될까 불안한 대학교 2~3학년 |
| 사용 상황 | 유출 뉴스를 본 직후 스마트폰 세로 화면으로 2~3분 안에 확인 |
| 제약(가설) | 회원가입·아이디·비밀번호 입력을 꺼림, 어려운 보안 용어는 부담, 출처가 불분명한 정보는 신뢰하지 않음 |

- 근거(3주차 문서 기재): 통계청 사회조사(2024)에서 국민의 57.6%가 개인정보가 안전하지 않다고 답했고 개인정보 유출이 가장 높은 불안 항목이었다. 유출 신고는 2024년 307건, 2025년 447건이다. 개인정보위·KISA '털린 내 정보 찾기'는 아이디·암호 입력과 본인 인증이 필요한 방식이다(직접 사용해 확인한 것은 아님).
- 한계: 대학생이 유출 사고 후 실제로 서비스별 확인을 하는지는 자료를 찾지 못했다. 10~20명 간이 설문을 계획했고(질문 예: 최근 유출 뉴스를 보고 내 계정을 확인해 본 적이 있는가, 어디서 확인했는가, 무엇이 막혔는가), 실제로는 10명 미만에게 진행했다. 결과는 노션이 아닌 다른 곳에 정리해 두었고, 대다수가 뉴스에서 유출 소식을 접했으며 확인할 때 막힌 점은 "내 정보가 어디까지 유출됐는지"를 알기 어렵다는 것이었다(요약은 2.2 참고). 가치 검증 기준(안)은 사용성 테스트에서 참가자가 내 서비스를 등록하고 관련 사고와 조치를 3번 이내 클릭으로 확인하는 것이다.

##### 문제 정의

> 유출 사고 뉴스를 접한 이용자는 사고 정보가 기사와 기관 공지에 흩어져 있어, 내가 쓰는 서비스가 해당되는지와 무엇이 유출됐는지, 무엇을 해야 하는지를 한 번에 확인하지 못하고 여러 자료를 찾아 읽어야 한다.

| 순위 | 문제 | 판단 근거 |
| --- | --- | --- |
| 1 | 내가 쓰는 서비스가 해당되는지 알기 어려움 | 확인이라는 핵심 목표를 직접 막고, 유출 뉴스마다 반복됨 |
| 2 | 유출 항목·시기·규모가 흩어져 있음 | 해당 여부를 확인한 뒤 판단 단계의 시간 손실 |
| 3 | 해당될 때 무엇을 해야 할지 모름 | 발생 빈도는 낮지만 행동으로 이어지는 마지막 단계라 영향이 큼 |

##### 기능 우선순위 (4주차)

| 우선순위 | 기능 |
| --- | --- |
| Must | 사고 목록 표시 / 내 서비스 등록·관련 사고 확인 / 서비스명·분야 검색 및 복수 필터 / 사고 카드 공통 항목 노출(유출 항목·시기·규모) / 사고 상세(유출 항목·시기·규모·출처) + 권장 조치 |
| Should | 시기·규모순 정렬 / 관심 사고 저장·최근 본 사고 / 유출 정보 종류별 대응 가이드 체크리스트(완료 상태 `LocalStorage` 저장, 진단 없이 진행 상태만 표시) |
| Could | 사고 비교 보기 / 최신 사고 외부 API 반영(심화 트랙 후보) |
| 제외 | 개인정보(아이디·비밀번호·이메일) 입력 기반 유출 여부 조회, 실시간 조회·알림, 사고 제보·댓글 등 사용자 생성 데이터, 뉴스 자동 수집·요약, 유출 여부·안전도 진단 판정 |

- 5주차에 사이트맵·User Flow에 추가된 기능: 최초 진입 시 걱정 항목 선택과 개인화 경고 배지, 사고 비교(4주차에는 Could였고 5주차에 목록의 선택 모드와 비교 화면으로 구현 범위에 포함), 내 서비스 사고 연표, 체크리스트 완료 도장·체크리스트 모아보기. 5주차 문서는 이 기능들을 "Must 기능 배치 확인" 표에 함께 적었고 우선순위 등급은 따로 적지 않았다.

##### MVP 정의와 질문 결과

> 사용자가 내가 쓰는 서비스를 등록하거나 검색·필터로 관련 사고를 좁힌 뒤, 목록의 카드에서 유출 항목·시기·규모를 비교하고, 상세에서 정확한 내용과 권장 조치를 확인해 무엇을 해야 하는지 알 수 있으면 MVP가 성립한다.

관심 사고 저장과 정렬은 Should로 두고, 체크리스트는 완료 여부 표시·저장까지만 제공하며 안전·위험 진단은 하지 않는다.

| MVP 질문 | 답 | 결과 |
| --- | --- | --- |
| 1. 첫 화면에서 무엇을 시작하는가 | 내 서비스 등록 또는 서비스명 검색 | O |
| 2. 어떤 조건으로 정보를 좁히는가 | 서비스명 검색, 서비스 분야 복수 필터, 내 서비스 기준 관련 사고만 보기 | O |
| 3. 어떤 정보를 보고 판단하는가 | 카드의 유출 항목·시기·규모 | O |
| 4. 상세정보를 어디서 확인하는가 | 상세의 유출 내용·권장 조치·공식 출처 링크 | O |
| 5. 다시 보고 싶은 항목을 어떻게 저장하는가 | 내 서비스(Must)·관심 사고(Should)를 id 목록으로 `LocalStorage`에 저장 | O (관심 사고는 Should) |
| 6. 결과가 없을 때 다음 행동을 알 수 있는가 | 조건 완화 안내와 초기화 버튼, 관련 사고가 없으면 "확인된 사고 이력 없음" 안내 | 설계 필요 (4주차 기준) |
| 7. 저장한 항목을 재방문 시 어디서 확인하는가 | "내 서비스 관리", "관심/최근 사고" 화면 | O |

- 6번은 4주차에 "설계 필요"로 남았다. 5주차에 결과 없음 상태와 예외 흐름을 설계했으나, 5주차 문서에서는 충족으로 다시 판정하지 않았다.

##### 사이트맵

4주차에는 5개 화면(홈, 사고 목록, 사고 상세, 내 서비스 관리, 관심/최근 사고)이었고, 5주차에 3개를 더해 8개 화면이 됐다. 모든 화면은 3단계를 넘지 않는다.

```
온보딩 (5주차 추가, 최초 1회)
홈
├─ 사고 목록
│  ├─ 사고 상세
│  └─ 사고 비교 (5주차 추가, 목록에서 2~3건 선택 시에만 진입)
├─ 내 서비스 관리
└─ 관심/최근 사고
   └─ 체크리스트 모아보기 (5주차 추가, 관심 사고에서만 진입)
```

- 화면을 늘리지 않은 판단: 보조 사용자 전용 화면, 최신순·규모순 보기, 내 서비스 관련 사고, 대응 가이드, 분야별 목록은 별도 화면 없이 목록의 필터·정렬이나 상세 하단 영역으로 처리했다. 홈 사고 현황 통계는 30건 기준의 신뢰도가 낮아 제외했다.

##### User Flow

| 흐름 | 단계 (5주차) |
| --- | --- |
| 흐름 A (처음 방문, 10단계) | 온보딩(걱정 항목 선택·건너뛰기) → 홈(최근 사고 3건·경고 배지) → 내 서비스 등록 → 사고 목록("내 서비스 모아보기") → 카드의 유출 항목·시기·규모 확인 → (선택) 비교 → 사고 상세(권장 조치·출처) → 관심 저장 → 체크리스트 완료(모두 완료 시 도장) → 목록 복귀(조건 유지) |
| 흐름 B (재방문, 7단계) | 홈(최근 사고 3건) → 내 서비스 관리 → 사고 연표 → 목록 또는 상세 → 관심/최근 탭 → 체크리스트 모아보기(저장 2건 이상) → 항목 체크 |
| 예외 흐름 | 비교 선택이 2건 미만이면 비교하기 버튼이 나타나지 않음 / 서비스는 있으나 관련 사고가 없으면 "등록된 데이터 기준 없음, 안전하다는 뜻은 아님" 안내 / JSON 로드 실패 시에도 `LocalStorage` 값은 유지 |

- 화면 상태: 5주차 문서는 "5가지 화면 상태"라고 쓰고 있으나 설계표에 정리된 상태는 초기·결과 없음·저장 완료 3개다.
- 사이트맵↔User Flow 대조에서 "보완 필요"로 남은 것: 홈에서 검색으로 사고 목록에 진입하는 경로, 관심·최근 사고 화면으로 이동하는 경로.
- 다이어그램(`A.png`, `B.png`, `55.png`)은 5주차 노션에 있다.

| 화면 | 핵심 기능 |
| --- | --- |

## 2. PRD 0.5

> 이 PRD는 **현재 구현된 사이트(v14)를 기준**으로 정리했다. 기획 단계(3~4주차)의 계획과 달라진 부분은 [2.10](#210-기획-대비-달라진-점)에 따로 적었다. 근거가 없는 내용은 추측해서 채우지 않았다.

### 2.1 배경과 문제 정의

- **상황**: 뉴스·SNS로 유출 사고를 접하면 "내 정보도 해당되나?"가 불안하지만, 사고 정보가 뉴스와 기관 공지에 흩어져 있어 내가 쓰는 서비스가 대상인지, 무엇을 해야 하는지 한곳에서 확인하기 어렵다.
- **기존 서비스와의 차이**: 개인정보위·KISA의 '털린 내 정보 찾기'는 아이디·암호(이메일)를 입력하고 본인 인증이 필요하다(3주차 조사 기준, 직접 사용해 확인한 것은 아님). LeakBase는 **개인정보 입력 없이** 사고 이력과 권장 조치를 제공한다.
- **문제 정의(핵심)**: 유출 뉴스를 접하고 불안한 이용자는 사고 정보가 여러 곳에 흩어져 있어, 내가 쓰는 서비스가 해당되는지와 필요한 조치를 한 번에 확인하지 못한다.

### 2.2 사용자

| 구분 | 내용 |
| --- | --- |
| 핵심 사용자 | 개인정보 유출이 불안해, 내가 이용하는 서비스의 사고 여부를 확인하고 대응하려는 일반 이용자(대학교 2~3학년 포함) |
| 보조 사용자 | 정보보안·개인정보보호 전공 대학생(과제·학습을 위한 사고 사례 조사·비교) |
| 제외 | 정보보안 분야 취업 준비생(3주차에 제외) |
| 사용 상황 | 뉴스로 유출 사고를 본 직후, 스마트폰 세로 화면으로 2~3분 안에 확인 |
| 제약 | 회원가입·아이디·비밀번호 입력을 꺼림(가설), 어려운 보안 용어는 부담(가설) |

- **근거의 한계**: 대학생이 유출 사고 후 실제로 서비스별 확인을 하는지는 자료를 찾지 못했다. 3주차에 간이 설문(10~20명)을 계획했고 **10명 미만에게 진행**했다. 결과는 노션이 아닌 다른 곳에 정리했으며, 대다수가 뉴스로 유출 소식을 접했고 확인할 때 막힌 점은 "내 정보가 어디까지 유출됐는지" 알기 어렵다는 것이었다. 표본이 작아 일반화하기는 어렵다. 사용성 테스트(내 서비스 등록 후 관련 사고·조치를 3번 이내 클릭으로 확인)도 아직 하지 않았다.

### 2.3 가치 제안과 목표

- **가치 제안**: 유출 사고 뉴스에 불안한 이용자에게, 내가 쓰는 서비스를 기준으로 사고 이력과 권장 조치를 보여 줘 무엇을 해야 하는지 바로 알게 한다. (불안 → 확인 → 행동)
- **MVP 성립 조건**: 사용자가 내가 쓰는 서비스를 등록하거나 검색·필터로 관련 사고를 좁힌 뒤, 목록 카드에서 유출 항목·시기·규모를 비교하고, 상세에서 정확한 내용과 권장 조치를 확인해 무엇을 해야 하는지 알 수 있다.
- **트랙**: 심화 트랙(최신 외부 API 반영) 선택. 필수 기능을 먼저 완성하고, API가 실패해도 저장 JSON으로 핵심 흐름이 유지되는 구조다. **현재 API는 연동하지 않았다.**

### 2.4 범위

| 구분 | 내용 |
| --- | --- |
| 포함 | 사고 목록·검색·복수 필터·정렬, 사고 상세(출처 링크·권장 조치 체크리스트), 내 서비스 등록·관련 사고 확인, 관심 사고·최근 본 사고, 사고 비교, 신고·상담 안내 |
| 제외 | 아이디·비밀번호·이메일 입력 기반 유출 여부 조회, 실시간 조회·알림, 사고 제보·댓글 등 사용자 생성 데이터, 뉴스 자동 수집·요약, 유출 여부·안전도 진단 판정 |

| 내 정보 | `pages/my.html` | "내 사고 목록"(등록한 서비스) / 관심 사고 / 최근 본 사고를 칩으로 전환. 서비스별 관련 사고 건수·삭제·연표 |
| 체크리스트 모아보기 | `pages/checklist.html` | 관심 사고별 체크리스트 진행도 |
| 신고·상담처 | `pages/help.html` | 개인정보침해 신고센터(118), 경찰청 사이버범죄 신고(182), 금융감독원(1332), 개인정보 분쟁조정위원회(1833-6972) 연락처와 "먼저 해볼 일" 안내 |
| (옛 주소) | `pages/saved.html` | 내 정보로 자동 이동 |

- **예외 처리**: 없는 사고 ID는 "사고를 찾을 수 없습니다"와 목록 버튼을 보여 준다. 값이 없는 필드는 "정보 없음"으로 통일한다. JSON 로드에 실패하면 오류 안내와 다시 시도 버튼을 보여 준다.
- **목록 조건 유지**: 검색어(`q`)·분야(`cat`)·유출 항목(`leak`)·유형(`type`)·내 서비스만(`mine`)·정렬(`sort`)을 모두 주소에 담아, 상세에서 돌아와도 조건·건수·정렬이 유지된다. 스크롤 위치는 `sessionStorage`(`lb-list-scroll`)로 복원한다.
- **실제·더미 구분**: 홈의 두 사고 영역은 실제 사고만 쓴다. 목록 결과에 더미가 섞이면 안내문이 뜨고, 더미 카드·상세에는 플라스크 아이콘과 "출처 없음" 안내가 나온다. 상세의 "비슷한 사고"는 실제에는 실제만, 더미에는 더미만 추천한다.

### 2.8 데이터 요구사항

**파일**: `data/accidents.json` (300건: 실제 167 + 더미 133, 필드 18개). 사용자별 값은 JSON에 넣지 않는다.

| 필드 | 의미 | 자료형 | 필수 | 검색·필터·정렬 |
| --- | --- | --- | --- | --- |
| `id` | 사고 번호(`KR-001`, 더미 `DM-001`) | String | 필수 | 상세 이동·비교·관심 저장 기준 |
| `title` | 사고명 | String | 필수 | 검색 |
| `company` | 사고 발생 기업·기관 | String | 필수 | 검색, 내 서비스 연결 |
| `category` | 서비스 분야(9종) | String | 필수 | 검색, 필터 |
| `incidentDate` | 발생일 | String/null | 선택 | 정렬 |
| `disclosedDate` | 최초 공개·신고일 | String/null | 선택 | 정렬(발생일이 없을 때) |
| `incidentType` | 사고 유형(5종) | String | 필수 | 필터 |
| `cause` | 원인 | String/null | 선택 | 표시 |
| `affectedCount` | 피해 규모(숫자) | Number/null | 선택 | 정렬 |
| `affectedUnit` | 피해 규모 단위(`명`/`건`) | String/null | 선택 | 표시 |
| `leakedData` | 유출된 개별 항목 | Array | 필수 | 표시 |
| `leakedCategories` | 유출 항목 대분류(5종, 복수) | Array | 필수 | 필터, 체크리스트 생성 |
| `penalty` | 처분·제재 내용 | String/null | 선택 | 표시 |
| `summary` | 한 줄 요약 | String | 필수 | 검색 |
| `sources` | 출처 목록 `{type, org, url, checkedAt, note}` | Array | 필수 | 표시(더미는 빈 배열) |
| `recommendOrder` | 홈 추천 순서(현재 화면에서 사용하지 않음) | Number/null | 선택 | — |
| `meta` | 출처·구분 정보 `{source, kind, real, dummy, draft}` | Object | 필수 | 실제·더미 구분 |
| `thumbnail` | 카드·상세 이미지 경로 | String/null | 선택 | 표시 |

**허용값**

| 항목 | 값 |
| --- | --- |
| 분야(9종) | 통신, 금융, 쇼핑·유통, 여행·숙박, 플랫폼·커뮤니티, 게임·레저, 공공, 교육·콘텐츠, 기타 |
| 유형(5종) | 해킹, 업무 과실, 시스템 오류, 내부자 유출, 기타 |
| 유출 항목(5종) | 계정정보, 금융정보, 연락처, 신원정보, 위치·이용기록 |
| 단위 | 명, 건 (섞어서 비교하지 않음) |

**데이터 규칙**

- 날짜는 `YYYY-MM-DD`(일·월을 모르면 `YYYY-MM` 또는 `YYYY`). 단일 값이 비면 `null`, 목록이 비면 `[]`, 빈 문자열은 쓰지 않는다.
- 피해 규모는 숫자와 단위를 함께 기록하고, 사람 수와 건수를 같은 것으로 보지 않는다.
- ID는 한 번 부여하면 재사용하지 않는다. 일부 ID(`KR-401`~`454`, `KR-328`~`330`)는 임시 번호이며, 수집이 끝나면 대응표와 함께 재부여할 예정이다.
- 사실은 출처로 확인된 것만 쓰고, 확인되지 않으면 `null`로 둔다.

**`meta` 구조**: `source`(`json`), `kind`(`real`/`dummy`/`api`), `real`(출처로 확인된 값이 있는 필드), `dummy`(가상 값 필드), `draft`(분류·요약 초안 필드: 실제 사고는 `category`, `leakedCategories`, `summary`).

**브라우저 저장(`localStorage`, 키 `leakbase`)**: `{ favs, recent, services, checks, cmp }` — 관심 사고 id, 최근 본 사고 id, 내 서비스 목록, 체크리스트 완료 항목(사고 id별), 비교 담기 id.

**대응 체크리스트 생성 규칙**: 모든 사고에 공통 2개("공식 공지·안내 확인", "다른 서비스와 같은 비밀번호 사용 여부 확인")를 두고, 사고의 유출 항목 대분류에 따라 항목을 더한다(계정정보 → 비밀번호 변경과 2단계 인증, 금융정보 → 결제·카드 이용 내역 확인, 연락처 → 스팸·피싱 주의, 신원정보 → 명의도용 확인, 위치·이용기록 → 이용 내역 확인). **사고별 조사 결과가 아니라 코드(`app.js`)에 둔 일반 권장 안내**다.

| 항목 | 내용 |
| --- | --- |
| 건수 | 300건 = 실제 167(`KR-`) + 더미 133(`DM-001`~`133`). API 0건 |

**정확성 기준**: 정부·규제기관 발표(개인정보보호위원회 등) > 기업 공식 공지 > 언론 보도 순으로 쓴다. 정부 사이트는 사람이 직접 열어 확인한 사고만 입고했다(입고 기준: 개별 사건, 유출 확정, 공식 출처 1개 이상, 직접 열람, 피해 11명 이상, 중복 제거, 업체별 분리). 분야가 `기타`인 사고가 많은 이유는 업종을 확인하지 못한 업체와 기업 간 거래(B2B)·제조 업체를 `기타`로 두었기 때문이다.

**더미 데이터**: 교수님께 말씀드려 양해를 받은 뒤, 공식 출처로 채우지 못한 133건을 생성형 AI로 만든 가상 사고(가상 기업명, 실존 기업 없음)로 채웠다. 실제 사건·사용자 수요를 검증하는 근거로 쓰지 않으며 기능 동작 검증용이다.

### 2.9 예정 기능과 외부 연동

**관련 뉴스·이슈 추적 기능** (추가 기능 탐색, **미구현**)

- 목적: 사고 이후 후속 보도(정부 조사, 기업 공지, 추가 피해 확인 등)를 상세에서 확인할 수 있게 한다.
- 구상: 상세에 "관련 뉴스" 영역을 추가하고, 최신순 정렬·새 기사 NEW 표시·중복 기사 제거·공식 발표와 언론 보도 구분을 제공한다. 뉴스는 GNews API로 가져온다.
- 구조(계획): GitHub Pages는 정적 호스팅이라 API 키를 브라우저 코드에 둘 수 없다. 그래서 GitHub Actions가 정기적으로 뉴스를 수집해 `news.json`으로 저장하고(키는 GitHub Secrets에 보관), 사이트는 이 JSON만 읽는다. `accidents.json`과 `news.json`을 분리해, 뉴스 영역에 문제가 생겨도 기존 검색·필터·상세·복귀 흐름은 그대로 동작한다.
- 상태: GNews 학생 무료 이용 프로그램(Student & Education Access) 신청과 추가 자료 회신까지 완료했고 **승인을 기다리는 중**이다(2026-11-15 기준). 요청 한도 등 실제 무료 이용 조건은 승인 후 확정된다.
- 구분 기록: 연동이 완료돼도 정기 수집한 저장 JSON을 읽는 방식이라 **실시간 조회가 아니다**. 데이터 출처·구분표의 연결 방식(현재 API 0건)에 이 점을 구분해서 기록한다.

**기타 예정**

- 홈 개편(히어로 이미지·등록 한 카드, 설명 줄이기, 사고 카드 테두리)과 톤앤매너(색 체계)는 v14에 반영함
- 히어로 이미지 3장은 적용했고, 제작 도구·제작일·프롬프트·후처리 기록은 `asset/hero/CREDITS.md`에 정리함
- 체크리스트 완료 도장(현재 미구현)

### 2.11 비기능 요구사항

- **모바일 우선**: 화면 폭을 393px(아이폰 16 기준)로 고정하고, PC에서는 가운데 정렬한다.
- **저장**: 서버·로그인 없이 `localStorage`만 사용한다. 사용자가 개인정보를 입력하지 않는다.
- **접근성**: 아이콘 버튼 레이블, 관심 저장 버튼 상태(`aria-pressed`), 동작 줄이기 설정 시 자동 이동 정지.
- **데이터 점검**: 페이지 로드 시 `checkData()`가 건수·필수 필드·자료형·ID 중복·허용값·출처 플래그를 점검해 Console에 출력한다(현재 300건, 경고 없음).
- **화면 안내**: 분야·유출 항목 분류와 요약은 팀 검토 전 초안이라는 안내를 상세에 표시한다.

### 2.12 미결정·한계

- 사용자 설문은 10명 미만의 소규모이고, 사용성 테스트 결과는 없음(2.2).
- 실제 휴대폰 점검은 v11까지만 했다. v12는 컴퓨터 브라우저(360px·390px)와 배포 화면에서, v13은 컴퓨터 브라우저(360px·390px)에서, v14는 컴퓨터 브라우저(Chromium 360px·393px)에서 확인했다.
- 홈 히어로 이미지 3장은 강조색이 장마다 다르다(핑크·파랑·주황). 10주차 교안에 강조색을 하나로 맞추라는 조건이 없어서, 바탕을 어두운 같은 톤으로 맞추는 것까지만 하고 강조색은 장마다 달라도 되는 것으로 정했다. 이미지 속 글자는 이미지 파일에 들어 있어 문구를 바꾸려면 이미지를 다시 만들어야 한다.
- 실제 사고 167건 중 기업 로고가 연결된 것은 63건. 나머지 104건은 회색 칸.
- 출처 열람일(`checkedAt`)이 빈 출처 11개 재열람 필요.
- 임시 ID(`KR-401`~`454`, `KR-328`~`330`) 재부여 예정.
- 규모순 정렬은 "명" 단위만 비교하고 "건"·값 없음은 뒤로 보낸다. 날짜가 없는 사고 67건은 최신순에서 맨 뒤.
- 일부 로고는 사고 당시와 다른 현재 로고이거나 그룹·글로벌 로고다(`asset/company/CREDITS.md` 참고).

## 3. 프로젝트 구성

- `index.html`, `pages/`: 화면
- `css/style.css`: 공통 스타일(색은 `:root` 변수로 관리, 카드·버튼·고정 헤더·정렬 버튼·필터 접기·홈 히어로 카드)
- `js/app.js`: 화면 동작. `data/accidents.json`을 fetch로 불러와 렌더링하고 Console에 `[데이터 점검]`을 출력
- `data/accidents.json`: 사고 데이터(JSON 저장 파일 사용, **API 미연동**). 각 항목의 `meta`에 출처 플래그(`source`, `kind`, `real`, `dummy`, `draft`)가 있음. `kind`는 `real`(실제)·`dummy`(더미)·`api`(API) 중 하나
- 데이터는 실제 사고 167건 + 더미(예시) 133건으로 총 300건. 더미는 생성형 AI로 만든 가상 사고이며 `meta.kind`가 `dummy`이고 화면에서 플라스크 아이콘으로 구분. 분야·유출 항목 분류와 요약은 팀 검토 전 초안(`draft`)
- GitHub Pages 주소에서 확인(파일을 더블클릭해 열면 fetch가 막힘)
- `asset/hero/`: 홈 히어로 이미지 3장(webp 1600×640). 수영 제작. 이미지 속 문구·변환 내역은 `asset/hero/CREDITS.md`에 기록. 이미지의 설명 문구(alt)는 `js/app.js` 홈 화면에 있음
- `asset/dummy/`: 더미 사고 카드에 쓰는 가상 기업 로고 40개. **AI 생성 실습용 이미지 · 실제 기업 로고 아님 · 실제 사고 사진 아님**. 수영 제작. 제작 도구·날짜·프롬프트는 `asset/dummy/CREDITS.md`에 기록. 로고 40개를 더미 133건에 같은 분야끼리 최신 사고부터 순서대로 돌려 가며 배정해, 같은 로고가 여러 사고에 반복된다. 각 사고의 `thumbnail` 필드(이미지 경로, 없으면 null)로 연결하고, 이미지가 없거나 불러오지 못하면 회색 칸으로 표시
- `asset/company/`: 실제 사고 카드에 쓰는 기업 로고 60개(사고 63건 연결). 출처 URL·확인일은 `asset/company/CREDITS.md`에 기록. 로고가 없는 사고는 회색 칸으로 표시

## 5. 기업 로고 안내

기업 로고는 각 기업의 상표이며, 본 프로젝트에서는 개인정보 유출 사고의 기업 식별 목적으로만 사용합니다. 본 프로젝트는 해당 기업과 공식적인 제휴 또는 관련이 없습니다. (학교 교육 과정의 비상업적 프로젝트입니다.)

`asset/dummy/`의 이미지는 생성형 AI로 만든 가상 기업 로고이며 실제 기업 로고가 아닙니다.

`asset/hero/`의 이미지는 생성형 AI로 만든 사이트 소개용 이미지이며 실제 기업 로고나 실제 사고 사진이 아닙니다.
